The **Credentials** page at `/credentials` answers one question: *where are my secrets, and how well are they protected?*

Every long-lived secret in the app — Jira and GitHub tokens, cache-server keys, external MCP headers, iOS signing keys, App Store Connect keys, APNs credentials — is written through a single server-only credential service. This page reports which backend that service is using, whether the payloads are actually encrypted, and what is stored. It never shows a value, and it is entirely read-only: each secret is managed in the settings form that owns it.

## Credential storage

The **Credential storage** card is the health check.

| Field | What it shows |
| --- | --- |
| **Backend** | Database, HashiCorp Vault, or macOS Keychain |
| **Protection** | AES-256-GCM, Plaintext, Vault KV v2, or Keychain |
| **Stored items** | How many credential records exist |
| **Backend mismatches** | How many records were written by a different backend than the one now active |

The card carries an overall state — **Ready**, **Warning**, or **Error** — alongside backend-specific detail: the Vault address, mount, path prefix, namespace, and TLS settings for Vault; the service name and host platform for Keychain; the storage location and encryption key status for the database.

### Warnings

Warnings are specific, and each names the fix.

| Warning | What it means |
| --- | --- |
| **Database encryption is disabled** | Payloads are plaintext because no encryption key is set |
| **Encryption key is invalid** | `CREDENTIAL_ENCRYPTION_KEY` is not strict base64 of exactly 32 bytes. Plaintext fallback is disabled while an invalid key is present |
| **Encryption key is missing** | Encrypted rows exist but the key is gone. Restore the original key and restart |
| **Encryption key does not match** | The configured key cannot decrypt the existing rows. Restore the original key and restart |
| **Credential data is invalid** | One or more records have unusable metadata |
| **Storage type is invalid** | `CREDENTIAL_STORAGE_TYPE` must be `database`, `vault`, or `keychain` |
| **Credential store is unavailable** | The backend could not be initialized; check configuration and logs |
| **Vault configuration is invalid** | Vault cannot start with the current address, headers, path, or TLS settings |
| **Vault uses plaintext HTTP** | Secret payloads and auth headers are unprotected in transit |
| **Vault certificate verification is disabled** | `VAULT_SKIP_VERIFY` accepts untrusted certificates |
| **Keychain is unsupported on this host** | The Keychain backend was selected on a non-macOS host |
| **Credentials use another backend** | Some records were written by a previous backend and must be re-entered |

## Stored credential items

The inventory table holds identifiers and protection metadata only.

| Column | What it shows |
| --- | --- |
| **Owning feature** | Jira, GitHub, Actions cache, External MCP server, iOS devices, Push notifications, or Notifications |
| **Credential kind** | What the record is — API token, personal access token, GitHub App private key, webhook secret, header bundle, profile signer private key, App Store Connect private key, APNs token key or certificate bundle, Web Push VAPID private key |
| **Updated** | When the value was last written |

To change any of these, open the settings form for its owning feature. Nothing on this page edits a value.

## Encrypting the database backend

The database backend stores payloads in plaintext until you give it a key. When that is the case, an alert on this page walks through the fix:

<Steps>
  <Step title="Generate a 32-byte key" icon="key">
    ```bash
    openssl rand -base64 32
    ```
  </Step>
  <Step title="Set it in the server environment" icon="settings">
    Set the generated value as `CREDENTIAL_ENCRYPTION_KEY`.
  </Step>
  <Step title="Restart the server" icon="refresh-cw">
    Existing plaintext rows are encrypted together on restart. No manual migration is needed.
  </Step>
</Steps>

<Warning>
  Back up this key and keep it for the lifetime of the encrypted rows. Losing or changing it makes every encrypted credential permanently unreadable — there is no recovery path and no key rotation.
</Warning>

## What is stored here

Long-lived Jira, GitHub, cache-server, external MCP, iOS-signing, App Store Connect, and APNs credentials all go through this server-only credential service. Pick a backend with `CREDENTIAL_STORAGE_TYPE` — see [Set up credential storage](/quickstart#set-up-credential-storage) for the configuration of each one.

## Vault options

Beyond `VAULT_ADDR`, the Vault backend accepts `VAULT_TOKEN`, `VAULT_NAMESPACE`, `CREDENTIAL_VAULT_MOUNT` (default `secret`), `CREDENTIAL_VAULT_PATH_PREFIX` (default `ai-development-environment/credentials`), and `CREDENTIAL_VAULT_HEADERS`.

`CREDENTIAL_VAULT_HEADERS` must be a JSON object of string values, and should be shell-quoted:

```bash
CREDENTIAL_VAULT_HEADERS='{"X-Vault-AWS-IAM-Server-ID":"vault.example.com"}'
```

Custom headers cannot override transport-managed headers or conflict with `VAULT_TOKEN` and `VAULT_NAMESPACE`. The page lists the *names* of any additional headers, never their values.

TLS options are `VAULT_CACERT`, `VAULT_TLS_SERVER_NAME`, and `VAULT_SKIP_VERIFY`. Plaintext HTTP and disabled certificate verification are supported, but produce prominent security warnings.

## Switching backends

Each metadata row records the backend that received its payload. Changing `CREDENTIAL_STORAGE_TYPE` does not migrate, read, or delete values from the previous backend: mismatched items are reported in **Backend mismatches** and must be re-entered through their owning settings forms.

<Warning>
  Backend-to-backend migration and encryption key rotation are intentionally unsupported. Switching backends is a re-entry exercise, so plan it when you have the source secrets to hand.
</Warning>

## Notes

- Secret values, ciphertext, authentication headers, and secret-derived previews are never returned to the browser — including on this page.
- The backend is selected with the `CREDENTIAL_STORAGE_TYPE` environment variable.
- Vault and Keychain outages do not take down the dashboard; only the features that need an unavailable credential fail.
- The `keychain` backend is loaded only on Darwin. Selecting it on Linux or in a container leaves the app running and reports an unsupported-backend error.
