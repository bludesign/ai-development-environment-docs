The **Builds** page at `/builds` holds build and imported-coverage history, plus the reusable JavaScript hooks that run around each iOS build. It has **History**, **Configurations**, and **Build Scripts** tabs.

Start a build from a [worktree](/worktrees/worktrees) or the repository Build cards on an [app overview](/apps/app-detail). The native Builds page also offers Start Build.

## History

Every build record appears newest first, with its status, captured configuration name, destination, duration, and artifact count. Saved configuration names link to [configuration details](/builds/build-configuration-detail). Deleted configurations retain their captured names without links. One-time builds explicitly show **Custom**.

An LCOV or Istanbul [coverage import](/builds/build-coverage#importing-coverage-from-other-test-runners) appears here as a `HOST` destination. That record ran no simulator or device build; it exists to hold the worktree snapshot, import status, logs, and coverage report.

| Status    | Meaning                                     |
| --------- | ------------------------------------------- |
| Queued    | Accepted, waiting for the agent             |
| Preparing | Setting up the build folder and environment |
| Running   | `xcodebuild` is executing                   |
| Succeeded | Completed with no failure                   |
| Failed    | The build or a script failed                |
| Canceled  | Stopped by hand                             |

Filter by status, select builds individually or a whole day at once, and **Delete selected**. The list pages with **Load more**.

Starting a build or coverage build closes its dialog and refreshes the surface where you started it. Rebuild behaves the same way. None of these actions automatically navigate to this page.

The build dialog offers **Any iOS Simulator** or **Any Physical iOS Device** immediately, then refreshes the live destination list in the background. You can start with the generic destination without waiting. If the refresh fails, the dialog shows a warning and keeps the generic destination available. The agent validates the scheme, configuration, and destination before running pre-build scripts. A failed Xcode preflight skips pre-build scripts and `xcodebuild`, but selected post-build scripts still run for cleanup. See [Execution and failures](#execution-and-failures).

<Warning>
  Deleting a build permanently removes the build record *and* its build folder —
  logs, products, archives, and exports. There is no undo.
</Warning>

## Saved and Custom configurations

Select **Custom** after the saved configuration cards to configure one build without saving a name or icon. On the web, Custom settings open inline below the configuration cards, so you can switch to a saved configuration at any time. Custom is selected automatically when the repository has an iOS App project but no saved configurations. Select an Xcode source, scheme, configuration, action, and build options using the same source inspection controls as the configuration editor, then choose **Use settings**.

For a selected configuration, **Physical Device** and **Simulator** tabs, the device picker, and build scripts stay visible. Expand **Details** for the source summary, action, advanced settings, export settings, and command preview. Archive requires a generic physical-device destination. Test Without Building requires compatible prior test products, including matching Custom source settings.

The **Configurations** tab lists reusable configurations with their repositories, icons, and settings. Open a card to inspect or edit it and review its paginated history.

## Choose the server URL for a build

The web and native **Start Build** sheets offer a **Server URL** selector with the name and URL on separate lines. It starts with the global default from [Settings](/system/settings#server-urls). Simulator destinations use the simulator default when configured, otherwise they inherit the global default. Switching destination type updates this suggestion until you explicitly choose Local, Remote, or Proxy.

The control plane snapshots all three base addresses, the selected kind, and the selected base address when it queues a build. Later settings changes do not change that queued build or its hooks. **Rebuild** retains the original kind and resolves its current configured address. Older builds without a recorded choice use current defaults. Rebuilding a Proxy build after removing Proxy fails with an actionable configuration error.

GraphQL `StartBuildInput.serverUrlKind` and MCP build inputs accept `LOCAL`, `REMOTE`, or `PROXY`. Omit the field to use the destination's default. Worktree coverage builds use the same selection and contract.

## Running on devices

**Run** opens the same detailed destination picker on Builds, Build Details, Worktrees, Worktree Details, Plan and Session build cards, and the Action Center.

- Agent tabs appear above device search. The Mac that produced the build is selected first and labeled **Build agent**; other macOS agents appear beside it. Offline, outdated, non-macOS, and known architecture-incompatible agents remain visible with a reason but cannot be selected.
- Switching agents clears the current device selection and loads that agent's destinations on demand. Search, **Select All**, **Clear**, quick run, and **Run Selected** always apply only to the active agent.
- Each row has a checkbox, the device name, and a second line with platform, OS version, and a humanized state such as **Connected**, **Offline**, or **Running**.
- Booted destinations appear first, followed by other available destinations and then unavailable ones. The first booted simulator is therefore the default when one is present.
- Select an available row anywhere except its play button to toggle it for a multi-device run.
- Use the trailing play button to run immediately on only that device without changing the multi-selection.
- **Select All** selects every runnable compatible device. **Clear** removes the selection. **Run Selected** stays visible in the picker and starts the selected destinations together once at least one is selected.
- Offline and otherwise unavailable devices stay visible for status awareness, but their selection and play controls are disabled.

Availability is rechecked by the server when a run starts. A device that disconnected after the picker opened is rejected instead of receiving stale work.

Running on the build agent uses the existing local path. For another agent, AIDE packages the runnable `.app`, uploads it into the control plane's authenticated artifact cache in resumable 16 MiB chunks, and has the target agent download, verify, extract, install, and launch it. The target does not need the source repository or worktree. If the package is already cached, a target agent can run it even when the original build agent is offline.

One Run action targets one agent, but it can still target several devices on that agent. Simulator architecture and minimum-OS metadata disable destinations known to be incompatible. Older builds without complete metadata are allowed through the picker and receive a final compatibility check on the target. Physical-device signing and provisioning requirements are unchanged.

Build rows containing an IPA also show **Install**. The action uses the newest eligible IPA. On a desktop browser, selecting its disabled-looking button opens: “Open this page on an iPhone or iPad to install.” HTTPS, bundle metadata, and export-method checks still apply. **Copy install link** copies that build's own page.

Every **Out of date** badge opens a menu with **Rebuild**. Queuing a rebuild refreshes the current page and displays any failure there.

## Build scripts

Open **Builds → Build Scripts** to create or edit reusable JavaScript hooks. On iPhone or iPad, open **Build Scripts**, tap **New Script** to create one, or select a script to edit it. Swipe a script to delete it. Both clients save the same definitions and repository assignments.

| Field | Notes |
| --- | --- |
| **Icon** | The same icon picker used by build configurations |
| **Repositories** | Search and select the repositories where the script is allowed |
| **Name** | Required, up to 80 characters after trimming; shown when selecting scripts for a build |
| **Pre-build JavaScript** | Code to run before `xcodebuild`; a default-exported function receives the [hook context](#hook-context) |
| **Post-build JavaScript** | Code to run after `xcodebuild` or during failure and cancellation cleanup; receives additional outcome fields |
| **Timeout in seconds** | A separate timeout for each hook, from 1 to 3600 seconds; defaults to 300 seconds |
| **Failure behavior** | **Fail the build** (`FAIL_BUILD`) or **Continue with a warning** (`CONTINUE`) |
| **Preselect this script for builds** | Initially selects it in Start Build; the native editor calls this **Enabled by default** |

Provide at least one non-empty pre-build or post-build script. Select the allowed scripts you want to run in **Start Build**. The preselection setting initializes the dialog; it does not make a script mandatory or select it for API callers.

<Warning>
  Build scripts are trusted Node.js ESM code. They run from the selected
  worktree root with a minimal environment, with the permissions of the agent
  account — treat them like any other code you would run on that machine.
</Warning>

<Note>
  Assign repositories directly in the script editor, or allow scripts from a
  repository's [details page](/codebases/repository-detail). Clearing the
  repository selection removes this script's assignments. New assignments from
  the script editor append to each repository's existing order. Other scripts
  keep their order. Scripts run only when selected for a build.
</Note>

### Author a hook

Each hook runs in its own Node.js process using the agent's Node.js executable. The agent saves the source as an `.mjs` file and imports it as an ES module. Top-level code runs when the module is imported. If you export a default function, the runner calls it with the context and awaits its result. A default export with any other type fails the hook.

Use `console.log` and `console.error` for output in the build log. A thrown error, rejected promise, non-zero process exit, or timeout fails the hook according to its **Failure behavior**. Each phase starts a new process, so in-memory state does not carry from the pre-build hook to the post-build hook.

The working directory is the worktree root, while the module itself lives under the build folder's `hooks/pre/` or `hooks/post/` directory. Relative filesystem paths resolve from the worktree root. Relative imports resolve from the generated module, and bare package imports search from that module's location rather than the worktree's `node_modules`.

To import a module from your checkout, construct an absolute file URL:

```js
import { resolve } from "node:path";
import { pathToFileURL } from "node:url";

export default async function preBuild({ worktree }) {
  const moduleUrl = pathToFileURL(
    resolve(worktree.folder, "scripts", "configure-build.mjs"),
  );
  const { configureBuild } = await import(moduleUrl.href);
  await configureBuild();
}
```

### Hook context

Both phases receive the following fields. `BUILD_CONTEXT_PATH` points to a JSON file containing the same context; the runner rewrites it before each hook.

| Field | Value |
| --- | --- |
| `buildId` | Identifier of this build |
| `branch` | Captured branch name, or `null` |
| `destination` | `type` (`SIMULATOR` or `PHYSICAL_DEVICE`), `id`, `name`, `platform`, nullable `osVersion` and `state`, and optional `generic` and `available` flags |
| `action` | `BUILD`, `TEST`, `ANALYZE`, `ARCHIVE`, `BUILD_FOR_TESTING`, or `TEST_WITHOUT_BUILDING` |
| `worktree` | `id`, absolute `folder`, nullable `branch`, and nullable captured `headSha` |
| `source` | Xcode source `kind` (`PROJECT`, `WORKSPACE`, or `PACKAGE`) and worktree-relative `relativePath` |
| `scheme` | Xcode scheme name |
| `configuration` | Xcode configuration name, such as `Debug` or `Release` |
| `server` | Captured Local, Remote, and Proxy bases, selected kind, and selected base; see the [server contract](#hook-server-and-endpoint-contract) |
| `endpointPaths` | Paths for app ingestion and symbol uploads, listed below |
| `telemetry` | Captured `consoleCollectionEnabled` and `analyticsCollectionEnabled` booleans |

Post-build hooks also receive these fields:

| Field | Value |
| --- | --- |
| `buildFolder` | Absolute path to this build's artifact directory on the agent |
| `failed` | Whether a build failure has been recorded before this hook runs |
| `cancelled` | Whether the build was cancelled |
| `errorCode` | Recorded failure code, or `null`; hook failures that fail the build use `SCRIPT_FAILED` |
| `error` | Recorded failure message, or `null` |

Check `failed` and `cancelled` independently. Cancellation can set `cancelled: true` while `failed` remains false. Outcome fields are evaluated before each post-build hook, so a failure in an earlier cleanup hook can affect later hooks.

### Hook server and endpoint contract

Both pre-build and post-build hooks receive these objects:

```js
export default async function preBuild({ server, endpointPaths, telemetry }) {
  const consoleUrl = new URL(endpointPaths.consoleLogs, server.selectedBaseUrl)
    .href;
  const analyticsUrl = new URL(
    endpointPaths.analyticsEvents,
    server.selectedBaseUrl,
  ).href;
  console.log("Selected server", server.selectedUrlKind);
  // Write these values and the collection flags into your app's build configuration.
}
```

`server` contains `localBaseUrl`, `remoteBaseUrl`, nullable `proxyBaseUrl`, `selectedUrlKind`, and `selectedBaseUrl`. `telemetry` contains `consoleCollectionEnabled` and `analyticsCollectionEnabled`.

| `endpointPaths` key  | Path                                     | Environment variable        |
| -------------------- | ---------------------------------------- | --------------------------- |
| `consoleLogs`        | `/api/telemetry/console-logs`            | `CONSOLE_LOGS_PATH`         |
| `analyticsEvents`    | `/api/telemetry/analytics-events`        | `ANALYTICS_EVENTS_PATH`     |
| `apnsRegistration`   | `/api/ios/apns-devices`                  | `APNS_REGISTRATION_PATH`    |
| `crashReports`       | `/api/public/crashes`                    | `CRASH_REPORTS_PATH`        |
| `dsyms`              | `/api/dsyms`                             | `DSYMS_PATH`                |
| `dsymUploads`        | `/api/dsyms/uploads`                     | `DSYM_UPLOADS_PATH`         |
| `dsymUpload`         | `/api/dsyms/uploads/{uploadId}`          | `DSYM_UPLOAD_PATH`          |
| `dsymUploadComplete` | `/api/dsyms/uploads/{uploadId}/complete` | `DSYM_UPLOAD_COMPLETE_PATH` |

Encode the upload identifier before replacing a dynamic placeholder:

```js
const path = endpointPaths.dsymUploadComplete.replace(
  "{uploadId}",
  encodeURIComponent(uploadId),
);
const url = new URL(path, server.selectedBaseUrl).href;
```

These paths cover app ingestion and symbol uploads. SSE, MCP, device enrollment, webhook, and other integration or administrative routes are excluded. Endpoint authentication and upload limits still apply.

### Environment variables

Both phases receive the following environment variables, alongside the path variables in the table above:

| Variable | Value |
| --- | --- |
| `BUILD_ID` | Current build identifier |
| `BUILD_PHASE` | `PRE_BUILD` or `POST_BUILD` |
| `BUILD_CONTEXT_PATH` | Absolute path to the current hook's JSON context |
| `BUILD_ARTIFACT_DIRECTORY` | Absolute path to this build's folder on the agent |
| `SERVER_LOCAL_BASE_URL` | Captured Local base address |
| `SERVER_REMOTE_BASE_URL` | Captured Remote base address |
| `SERVER_PROXY_BASE_URL` | Captured Proxy base address, or an empty string when unconfigured |
| `SERVER_URL_KIND` | `LOCAL`, `REMOTE`, or `PROXY` |
| `SERVER_BASE_URL` | Selected base address |
| `CONSOLE_LOG_COLLECTION_ENABLED` | String `"true"` or `"false"` |
| `ANALYTICS_EVENT_COLLECTION_ENABLED` | String `"true"` or `"false"` |

An unconfigured Proxy is `null` in the context and an empty string in the environment. Compare collection flags with `"true"` rather than testing the string's truthiness.

The runner inherits only these agent environment values when present: `PATH`, `HOME`, `TMPDIR`, `DEVELOPER_DIR`, `LANG`, `LC_ALL`, `USER`, `LOGNAME`, `SHELL`, and `SSH_AUTH_SOCK`. It also sets `TERM=xterm-256color`, `COLORTERM=truecolor`, `FORCE_COLOR=1`, and `CLICOLOR_FORCE=1` for terminal output. Other agent environment values are not inherited, and the runner does not automatically load a repository `.env` file.

### Execution and failures

Hooks run sequentially in the repository's assignment order, rather than the order of IDs submitted in `scriptIds`. Pre-build hooks run in ascending position; post-build hooks run in reverse position.

1. The agent validates the worktree and Xcode source. If these initial checks fail, no hooks start.
2. Xcode preflight validates the scheme, configuration, and destination. A failed preflight skips all pre-build hooks and the main `xcodebuild` invocation.
3. Selected pre-build hooks run one at a time. A failure with `FAIL_BUILD` stops the remaining pre-build hooks and prevents `xcodebuild`. With `CONTINUE`, the failure is recorded and the build proceeds.
4. `xcodebuild` runs if preflight and pre-build hooks allow it and the build has not been cancelled.
5. All selected post-build hooks run in reverse order for cleanup, including after a failed preflight, failed pre-build hook, failed `xcodebuild`, or cancellation. A script's post-build hook can run even when its pre-build hook was skipped. Failure in one post-build hook does not skip the remaining post-build hooks.

The timeout applies independently to each pre-build and post-build invocation. A timeout terminates that hook process and records `TIMED_OUT`. `FAIL_BUILD` turns a hook failure into a build failure; `CONTINUE` preserves the recorded hook failure while allowing the remaining work to proceed. A post-build failure can change an otherwise successful build to failed.

Cancelling the build stops the active pre-build hook or `xcodebuild`. Post-build hooks use a separate cancellation signal, so they still run with their own timeouts. Cancellation can therefore take longer than stopping the build command alone. A failure in cleanup does not replace a cancelled build's final cancelled status.

### Edit, delete, and rebuild

When you queue a build, the control plane captures each selected script's source, name, order, timeout, and failure behavior. Editing or deleting the library script, or changing its repository assignments, does not change hooks already captured for that build.

**Rebuild** selects the original script IDs but reads their current library definitions, limits, and repository order. It does not replay the old source text. If a selected script has been deleted or is no longer allowed for the repository, rebuilding fails validation. Start a new build with an allowed selection instead.

Deleting a script removes it from the library and clears its repository assignments. The control plane retains its stored definition as a deleted record, and existing builds keep their execution snapshots.

### Stored source, context, and logs

The control plane stores library source, each build's script snapshot, and per-phase execution records. On the agent, the build folder contains `context.json`, generated `.mjs` sources and runners under `hooks/pre/` and `hooks/post/`, per-hook `.log` files, and the combined `build.log`. These files remain with the build folder after execution. Use **Delete build** to remove that build's history and folder.

<Warning>
  Script text, context files, generated files, and logs can contain sensitive
  values. Avoid embedding credentials in source or printing secrets. Deleting
  a library script does not erase its stored definition or historical copies.
  Review script text before including it in an [app export](/apps/import-export).
</Warning>

Inspect phase status and errors in the **Scripts** section of [Build Details](/builds/build-detail#script-executions), and use the build log to investigate output.

## Worktree coverage

**Run Worktree Coverage** runs tests with coverage and measures the executable lines changed in the current branch and working tree — a coverage number scoped to the change rather than the whole project. Reports appear on the [worktree details](/worktrees/worktree-detail) page.

For a non-Xcode test suite, a workflow or MCP client can instead [import an LCOV or Istanbul report](/builds/build-coverage#importing-coverage-from-other-test-runners). Imported reports appear in the same worktree coverage list and on the [Changes](/changes) page.

## API inputs and compatibility

`startBuild` and `inspectBuildDestinations` accept exactly one of `configurationId` or
`customConfiguration`. Custom settings contain `sourceKind`, `sourcePath`, `scheme`, and
`buildConfiguration`; action, destination, scripts, advanced settings, and export options
remain separate inputs. Custom runs create no saved configuration. Their snapshots retain
an explicit Custom marker and the settings required by `rebuildBuild`.

Use `buildConfigurations` and `buildConfiguration(id:)` for saved settings. Build history
accepts `configurationId` and `repositoryId` filters. Repository `latestBuild` is the newest
record across all worktrees and agents, including failed and running builds.

Use `buildScripts` to list active scripts, `saveBuildScript(input:)` to create or update one, and `deleteBuildScript(id:)` to remove it. `setCodebaseBuildScripts(codebaseId:, scriptIds:)` replaces the shared repository's allowed list in the supplied order; it applies across that repository's checkouts. Subscribe to `buildScriptsChanged` to refresh after saves, deletions, or assignment changes. MCP exposes `get_build_scripts`, `save_build_script`, and `delete_build_script`.

Script saves accept nullable `iconKey` and optional `repositoryIds`. Omit a field to preserve its value; `iconKey: null` clears the icon, and an empty repository array clears this script's assignments. Saving the script and its assignments is transactional.

Pass `scriptIds` explicitly to `startBuild`, `startWorktreeCoverage`, or their MCP equivalents. Omitting the field or supplying an empty list runs no scripts, including those marked `enabledByDefault`. The control plane validates that every requested script is active and allowed for the worktree's repository, ignores duplicate IDs, and uses the repository's saved execution order.

`deleteIosAppProject(id:)` removes project settings, sources, and observations after the UI
confirmation. It rejects repositories with an active build, including Custom runs, and keeps
build history, artifacts, repository files, and script assignments.

## Notes

- Build records are immutable. Each build gets its own folder for logs, products, archives, and exports, so two builds never overwrite each other's output. The folder location is set per agent under **Builds directory** on the [agent detail page](/agents/agent-detail).
- Successful builds that produced a runnable app and have never been deployed surface in the [Action Center](/dashboard) as **Ready to run**.
