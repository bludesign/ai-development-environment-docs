The **Action Center** is the home screen at `/dashboard/action-center`. It is a single queue built from six resource types — AI Plans, AI Sessions, iOS builds, workflow runs, GitHub pull requests, and GitLab merge requests — so anything that is running, stuck, failed, or waiting on you appears in one queue.

Nothing is added by hand. The control plane derives the list from the current state of each resource, so an item disappears on its own as soon as the underlying work moves on.

## Page URLs and breadcrumbs

Web page URLs follow the sidebar section: `/dashboard/...`, `/ai/...`, `/debugging/...`, `/github/...`, `/gitlab/...`, `/jira/...`, and `/system/...`. For example, open `/github/pull-requests` for **GitHub Pull Requests** or `/system/settings` for **Settings**.

These paths omit the locale prefix. An English URL starts with `/en`, such as `/en/dashboard/action-center`. Opening the site root or a locale root takes you to the Action Center. Previous URLs for moved pages have no redirects; update saved bookmarks and shared links.

The title-bar breadcrumb shows the section and page, such as **GitHub → Pull Requests** or **GitLab → Cache**. GitHub and GitLab page headings include the provider name, while the sidebar and breadcrumbs keep their shorter labels. The `/api/...` endpoints and `/graphql` subscription URL keep their existing paths.

An item is a resource plus the reason it earned a place in the queue.

## Why an item appears

Every item carries one **reason** badge. The reason also sets the item's position — the list is sorted by reason first, then by most recently updated.

| Reason | Badge | Meaning |
| --- | --- | --- |
| Answer needed | Amber | A pending question batch is waiting on your input. |
| Blocked | Neutral | A workflow run is blocked, or a Plan or Session landed in a failed phase. |
| Failed | Red | The resource finished in a failed state and has not been acknowledged. |
| Ready to run | Blue | A successful build produced a runnable app that has never been deployed. |
| Approval required | Amber | The connected account is requested to review a pull request or merge request. |
| Ready to merge | Green | The provider confirms that the request can merge. |
| Active | Green | Work is queued or in progress and needs nothing from you. |

Questions, blocked or failed work, ready-to-run builds, approval requests, and merge-ready requests are grouped under **Needs attention**. Only **Active** items land in the **Active** section.

<AccordionGroup>
  <Accordion title="How “Blocked” is decided" icon="circle-exclamation">
    For a workflow run, **Blocked** simply means the run's status is `BLOCKED`.

    For a Plan or Session, the status is still in progress but its **phase** ended in a failure — any phase whose name ends in `_FAILED`, plus the special `IMPORTED_ACTIVE_COLLISION` phase, which means an imported run collided with one that was already active.
  </Accordion>
  <Accordion title="How “Ready to run” is decided" icon="circle-play">
    A build is offered as ready to run only when every one of these holds:

    - It is the most recent build for its worktree, configuration, and destination combination.
    - Its status is **Succeeded**.
    - Its worktree is still present on disk and marked available.
    - It produced a runnable app artifact.
    - It has no deployment records — nobody has installed or run it yet.

    Run it straight from the card. The detailed picker starts on the build agent, can switch to another eligible Mac, shows compatible available and unavailable destinations, supports search and checkbox multi-selection, and includes a per-device quick-run button. A cross-agent run transfers the app through the authenticated artifact relay.

    **Dismiss** hides this particular unrun build without marking it as deployed. The server accepts dismissal only while it is still the newest successful, runnable, undeployed build for its worktree, configuration, and destination.

    The dismissal fingerprint includes the build ID. A newer successful build gets a different fingerprint and appears again.
  </Accordion>
  <Accordion title="How a failure is tracked" icon="fingerprint">
    Each failed item gets a **failure fingerprint** built from its kind, id, generation, and the time it finished. Acknowledging stores that fingerprint and hides the item.

    Because the finish time is part of the fingerprint, a later failure of the same resource produces a new fingerprint and reappears. Acknowledging never suppresses a future failure.
  </Accordion>
</AccordionGroup>

## Using the page

<Steps>
  <Step title="Scan the counters" icon="hashtag">
    Three badges under the title show the total item count, how many need attention, and how many are active. They reflect the whole queue, not just the page you have loaded.
  </Step>
  <Step title="Work the Needs attention section" icon="triangle-exclamation">
    Items are already ordered by urgency — questions first, then blocked, failed, and ready-to-run. Each card links to the full Plan, Session, build, or run.
  </Step>
  <Step title="Answer any questions inline" icon="circle-question">
    Pick from the offered options, or type a **Custom answer** when the question allows one, then **Submit answer**. See below for the details.
  </Step>
  <Step title="Acknowledge failures you have handled" icon="check-double">
    **Acknowledge** clears a failed item from the queue without touching the underlying resource.
  </Step>
  <Step title="Dismiss an unrun build" icon="xmark">
    **Dismiss** removes a ready-to-run build from the full or compact Action Center. The UI removes it immediately and refreshes the counters; a stale dismissal is rejected if the build stopped being the current eligible candidate.
  </Step>
  <Step title="Page through the rest" icon="angles-down">
    The list loads 50 items at a time. **Load more** appends the next page.
  </Step>
</Steps>

### Answering a question

Question batches come from Plans and Sessions directly, and from workflow runs by way of the step attempt that raised them — the card labels the source as **Question from …**.

- **Single choice** questions render as radio options. Picking an option clears any custom text you typed, and typing custom text clears the selection.
- **Multiple choice** questions render as checkboxes, and a custom answer is appended alongside whatever you checked.
- **Custom answer** is only offered when the question permits it.
- **Submit answer** stays disabled until every question in the batch has either a selection or non-empty custom text.

<Note>
  Answers are submitted for the whole batch at once. If a batch asks three questions, all three must be answered before you can submit.
</Note>

## Pull requests and merge requests

  <img className="block dark:hidden" src="/images/light/action-center-pull-requests.png" alt="Action Center pull requests in light theme" />
  <img className="hidden dark:block" src="/images/dark/action-center-pull-requests.png" alt="Action Center pull requests in dark theme" />
</Frame>

The full queue includes GitHub **Mine** requests (authored or assigned), GitLab requests you authored, and requests asking the connected provider account to review. A request that belongs to both categories appears once. Drafts remain visible with a **Draft** indicator; closed and merged requests leave the queue after refresh.

Each card shows its provider, repository, branch, pipeline status, and overall approval status. Open the pipeline link to inspect checks. A green **Merge** button opens the existing provider merge dialog, where you review the current commit, available merge method, and optional follow-up actions. The dialog checks readiness again before merging. Unknown or blocked readiness does not show a green button.

Approving a request removes its review-category membership. Your own or assigned requests remain visible even when approved, so you can merge them. A dismissed or revoked approval makes a request eligible for the review queue again. Overall approval and your personal approval are separate: a request can still need other reviewers after you approve it.

Open **System → Settings → Action Center** to configure shared preferences:

| Setting | Default | Behavior |
| --- | --- | --- |
| **Maximum request age (days)** | `30` | Excludes requests created more than this many days ago. Set `0` to disable the cutoff. Applies to the full and compact queues and the provider request totals. |
| **Show my open requests in sidebar** | On | Includes the Mine category in the compact queue. |
| **Show requests awaiting my approval in sidebar** | On | Includes requests awaiting your approval in the compact queue. |
| **Confirm before clearing all notifications** | On | Asks you to confirm before clearing the web notification sidebar. Dismissed notifications remain in history. |
| **Show pull/merge request and Actions/Pipelines counters** | On | Shows provider totals in the web sidebar and enables their dedicated CI polling. |
| **Show Dirty and Off Main counters** | On | Shows saved worktree totals in the web sidebar. |

The two request-category switches are independent. Turning either off leaves its category available in the full Action Center and in the provider request totals. Queue counts and pagination reflect the selected surface, including filtering before a page is read. Dedicated GitHub and GitLab request lists retain their own filters.

Select **Save settings** to apply changes. Open web sidebars update through live settings notifications. Hiding provider counters stops their dedicated sidebar CI polling and clears those cached counts; Action Center discovery and notification polling continue. Showing the counters again starts a fresh refresh.

The iOS app exposes the same shared request-age and request-category settings, request statuses, native detail screens, and merge sheets. On iPad, the navigation sidebar also includes a compact request queue; iPhone uses the full Action Center.

Request summaries are stored in the control plane database and refreshed on startup, every 60 seconds, and after relevant provider events. Provider response caches still apply. **Refresh** rebuilds the index using those caches. If discovery fails or hits a provider limit, the queue shows a warning and preserves previously available entries; merge readiness is not confirmed for that provider until a successful refresh. Changing or disconnecting an account removes its old index entries during reconciliation. The index contains request metadata, not provider tokens.

## Sidebar and iOS totals

The bottom-left web sidebar shows activity totals alongside spend and disk status. Open **Status Center** in the native iOS app for the same totals. Select a counter to open its corresponding page.

| Web counter | iOS counter | What it counts |
| --- | --- | --- |
| **Actions** | **Actions** | Items in the full Action Center queue. |
| **Pull Reqs** | **Pull Requests** | Open GitHub requests in **Mine** (authored or assigned), plus requests awaiting your approval. |
| **Actions** | **Actions** | GitHub Actions workflow runs that are running or queued to start across your managed repositories. |
| **Merge Reqs** | **Merge Requests** | Open GitLab requests you authored, plus requests awaiting your approval. |
| **Pipelines** | **Pipelines** | Active GitLab pipelines from your managed projects, including preparing, queued, running, and canceling pipelines. |

With provider counters enabled, the GitHub request and **Actions** counters appear when GitHub is configured. The GitLab request and **Pipelines** counters appear when GitLab is configured. Connecting both providers shows all four counters; a configured provider with no matching activity shows `0`.

A request that is both yours and awaiting your review counts once. Review requests leave the total after you approve them, even if other reviewers still need to approve. Your own or assigned requests remain counted after approval. The saved **Maximum request age (days)** applies to both request counters: the default is `30`, and `0` includes every age. The compact queue's two visibility switches do not change these totals.

Completed runs and pipelines in **Manual** or **Scheduled** states are excluded from the active CI totals. These totals refresh in the background and through live updates. During a temporary provider failure, the control plane retains the last successful count for the same connection. A configured provider shows `—` until its count is available.

### Worktree counters

The web sidebar also shows **Dirty** and **Off Main** when **Show Dirty and Off Main counters** is enabled:

| Counter | What it counts | Opens |
| --- | --- | --- |
| **Dirty** | Worktrees with staged or unstaged changes. | Worktrees with **Dirty worktrees** and all branches selected. |
| **Off Main** | Worktrees off a known repository default branch, including detached HEADs. The default branch can have any name. | Worktrees with all change states and **Not on default branch** selected. |

These totals use saved reports across agents, include hidden worktrees, and exclude missing worktrees. **Off Main** excludes repositories whose default branch is unknown. The links select the corresponding changes and branch filters; other filters and the [Active Agent selector](/worktrees/worktrees#use-the-active-agent) still apply. See [Finding a worktree](/worktrees/worktrees#finding-a-worktree).

## Mini Action Center

The app shell carries a compact copy of the same queue in the sidebar, showing the total count and a condensed row per item — title, reason badge, the first pending question, any error, and the linked worktree. It shares state with the full page, so answering, acknowledging, running, or dismissing in one place updates the other immediately. The iOS list exposes **Dismiss** as a swipe action and repeats it on Action Center details.

## Live updates

The queue subscribes to an `actionCenterChanged` subscription and refetches whenever the control plane signals a change. It also refetches on every reconnect, so a dropped WebSocket cannot leave stale items on screen. **Refresh** forces the same reload by hand.

<Tip>
  When a Plan, Session, build, or workflow run is tied to a worktree, the card shows the worktree's folder and branch and inherits its highlight color as a left border stripe — useful for telling parallel work on the same repository apart at a glance.
</Tip>

## Discovery through MCP

`get_action_center` reads this queue with `first` (1–200, default 50) and an optional `after` cursor. It returns active work, pending questions, blocked or failed resources, builds awaiting action, and pull or merge requests with provider status. It does not acknowledge or dismiss items.

Use `global_search` to locate resources across the development environment. Its `query` is required and limited to 200 characters; `firstPerGroup` is 1–10 (default 5) and `relatedFirst` is 0–5 (default 3). Add these read-only tools to an [MCP preset](/system/tools#mcp-tool-presets) to help an AI find the resource it needs.
